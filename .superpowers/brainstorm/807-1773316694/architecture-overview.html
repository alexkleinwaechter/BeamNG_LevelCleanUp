DecalRoad Generation — Architecture Overview

Three approaches for the core generation engine. Click to select your preferred approach.

A

Spline-First Architecture (Recommended)

Core idea: Generate DecalRoads directly from ParameterizedRoadSpline objects, using cross-section data for elevation and width.

UnifiedRoadNetwork (splines + junctions)
    ↓
DecalRoadLayerSetResolver — picks layer set per spline
    │ cascade: OSM type override → material fallback → defaults
    ↓
DecalRoadGenerator — for each spline × each layer:
    │ 1. Sample centerline nodes
    │ 2. Apply lateral offset (position × width × binormal)
    │ 3. Look up Z from heightmap
    │ 4. Transform to BeamNG world coords
    │ 5. Chunk into ≤100-node segments
    ↓
JunctionInterrupter (Phase 1) — cuts markings at junction zones
    ↓
DecalRoadSceneWriter — writes NDJSON to items.level.json

Pros

  • Reuses existing spline sampling from MasterSplineExporter
  • Natural per-spline iteration matches layer set override system
  • Junction interruption is simple: check distance to junction centers
  • Each spline retains its OSM road type for layer set resolution

Cons

  • Edge markings at junctions won't follow merged contours (Phase 1 limitation)
  • Overlapping splines generate overlapping DecalRoads (render priority resolves visually)
B

Network-First Architecture

Core idea: Compute a unified road surface mesh/boundary first, then derive DecalRoads from the network topology.

UnifiedRoadNetwork
    ↓
RoadSurfaceBuilder — compute merged road polygons
    │ union all road strips, compute outer contour
    ↓
ContourExtractor — extract edge contour polylines
    ↓
Edge DecalRoads from contours + Inner markings from splines
    ↓
DecalRoadSceneWriter

Pros

  • Perfect junction edges from day one
  • No overlapping edge markings at junctions

Cons

  • Requires computational geometry library (polygon union, contour tracing)
  • Loses per-spline identity at edges — harder to apply per-type layer sets
  • Much more complex, harder to debug, longer to implement
  • Still needs spline-based approach for inner lane markings
C

Hybrid: Spline-First + Contour Phase 2

Core idea: Start with Approach A (spline-first) for everything. Plan the architecture so contour-based edges can be swapped in later for Phase 2.

Phase 1: Approach A (spline-first, junction interruption)
    ↓ ships first, works well for most roads
Phase 2: Add ContourEdgeGenerator as alternative edge source
    │ Plugs into same DecalRoadSceneWriter
    │ Only replaces edge layer generation at junctions
    ↓ inner markings still spline-based

Pros

  • Ships fast with Approach A
  • Architecture supports Phase 2 contour upgrade
  • Inner markings stay simple (spline-based) forever

Cons

  • Phase 1 junction edges are basic (interruption only)
  • Need to design interfaces that accommodate both approaches
